# Окружение и запуск

## Зависимости

    pip install -r requirements-dev.txt

Продуктовая зависимость одна — `aiohttp` (см. `requirements-console.txt`).
`yarl` и `multidict` приходят с ней. Тесты дополнительно требуют `pytest`.
Прогон выполнялся на Python 3.12.3.

## Прогон тестов

    bash RUN_TESTS.sh

Ожидается `226 passed, 64 subtests passed`.

Оба набора обязаны идти в одном процессе против одного релиза: каждый файл
кладёт свой каталог релиза в `sys.path` и импортирует `profile_store`, а Python
кеширует модуль — при смешивании релизов молча тестируется тот, кто
импортировался первым. `RUN_TESTS.sh` это фиксирует переменными
`PAP_CONSOLE_RELEASE` и `PAP_RECEIVER_RELEASE`.

Прогнать набор против закрытого среза 1 (регрессия основания):

    PAP_CONSOLE_RELEASE=4.5.0-s1 PAP_RECEIVER_RELEASE=2.11.0-s1 bash RUN_TESTS.sh

## Проверка карты точек врезки

    cd tools
    python3 verify_inventory.py     # 177 проверок
    python3 verify_overlaps.py      # 10 проверок
    python3 verify_map.py           # 212 проверок

Все три обязаны давать `failures=0`. `verify_map.py` в том числе запускает
`extract_inventory.py` и требует, чтобы тот побайтно воспроизвёл приложенную
`inventory.json` — пакет с оснасткой и артефактом разных поколений не пройдёт.

Пути в оснастке вычисляются от её собственного расположения, поэтому дерево
можно распаковать куда угодно, и запускать проверку можно из любого каталога.
`verify_map.py` пишет отчёт рядом с собой; путь можно задать явно первым
аргументом.

Числа следуют карте, а не наоборот, и подгонять их к запомненным не нужно.
Прежние 203 нормой не являются: проверка `archive sha256` удалена как хвост
модели идентичности, к которой принадлежал удалённый `baseId` — основание
подтверждают `working base subtrees match git` и `working base clean`. Дальше
числа выросли от строк карты `MAP-083…087`, приёмок `ACC-S2-033…037`, `ACC-S5-026` и двух
новых якорей (`attachment_chunk`, `_touch_lease`) в каталоге инвентаря.

Проверка whitespace выполняется по рабочему дереву без evidence-каталогов:

    git diff --check -- . ':(exclude)review*/**'

`reviewNN/` содержит сохранённые логи и patch-файлы ревью; это доказательства
прогона, а не исходники продукта. Обычный `git diff --check` в текущем Git-снимке
тоже чист, потому что evidence-каталоги не отслеживаются, но явное исключение
делает команду устойчивой к способу упаковки/сравнения у внешнего ревьюера.

## Запуск платформы локально

    bash start_platform.sh

Скрипт идемпотентен: менеджер стартует, только если ещё не жив. Он поднимает
receiver на 8867 и консоль на 8871, дожидается готовности и печатает
`RET_VALUE::PLATFORM2_READY=1`.

Перед первым запуском нужен маркер релиза консоли:

    python3 activate_console_release.py 4.5.0-s1

Маркер receiver необязателен: без него запускается корневой `server.py`
(режим `legacy`), что и есть состояние до среза 1.

**Перезапуск нельзя выполнять командой, которую исполняет сама платформа** —
дерево процессов умрёт вместе с выводом. Только отдельным скриптом:

    setsid bash rollout_slice1.sh activate > /tmp/rollout.log 2>&1 < /dev/null &

## Выкат и откат среза 1

    setsid bash rollout_slice1.sh activate  > /tmp/rollout.log 2>&1 < /dev/null &
    setsid bash rollout_slice1.sh rollback  > /tmp/rollout.log 2>&1 < /dev/null &

`activate` ставит консоль `4.5.0-s1` и receiver `2.11.0-s1`, `rollback`
возвращает `4.4.0` и `2.10.0`. Оба маркера пишутся **до** остановки, чтобы
менеджер мог подняться только на целостной паре.

Успешный результат содержит `RET_VALUE::ROLLOUT_RESULT=OK` и обе версии в
`HEALTH_*`.

## Живой smoke

    bash smoke_slice1.sh

Проверяет поведение, а не версии: приём Run, дедупликацию одинакового разбора,
отсутствие staging в списке, единственность canonical, связь снимка и
разрешённого контекста. Пишет два тестовых Run в `data/`.

## Чего в дереве нет

`data/`, `config/`, `runtime/`, `logs/` — состояние конкретного развёртывания:
содержимое чатов, профили, секреты, маркеры. Тесты создают всё нужное во
временных каталогах. Для живого запуска профиль и привязку создаёт оператор
через интерфейс консоли.

`console_releases/4.3.5` — замороженный исторический релиз, существует только
на сервере, в передачу не попал. Он ничем не используется: активным был
`4.4.0`, к нему привязаны HISTORICAL-строки карты, и он здесь есть.
