# Prompt Automation Pro 2 — дизайн 4.5.0

Редакция 34 (2026-09-05). **Проектная часть закрыта.** Работа над документом ведётся несколькими заходами.
Разделы 1–5 закрыты и служат основанием для остальных. Разделы 6+ пишутся
следующими заходами и не должны противоречить закрытым решениям.

Основание: фактически развёрнутые Console 4.4.0 r7 и расширение 2.11.6.

## 1. Цели

Профиль становится задачей с намерением: конфигурация объявляет, должна ли задача
работать, а система приводит фактическое состояние к объявленному. Вкладки
открываются как следствие намерения, а не как его предпосылка. Оператор,
расписание и конфигурация меняют только намерение.
Адресация переходит от вкладки к переписке. Исполнение директив впервые
меняется: появляется generic-разбор и action pipeline.

## 2. Инварианты, которые не нарушаются ни одним срезом

1. Нет исполнения и нет отправки без включённой привязки к включённому профилю.
2. Проверка авторизации выполняется живьём при каждом действии; провенанс
   фиксируется и не пересчитывается.
3. Нет тихой подмены собеседника: при неоднозначности система спрашивает, а не
   выбирает сама.
4. Явное «выключено» оператора действует в обе стороны — на вход и на выход.
5. Значения секретов не попадают ни в один артефакт: ни в план, ни в состояние,
   ни в снимок сессии, ни в события, ни в журналы, ни в API.
6. `executor.py` и `protocol_engine.py` меняются только в том срезе, который
   заявлен как ломающий, и никогда попутно.

## 3. Модель

| Сущность | Хранение | Природа | Отвечает на вопрос |
|---|---|---|---|
| Profile | `config/profiles/<id>/` | постоянная | что за работа и как её делать |
| Binding | `config/chat-bindings.json` | постоянная | какой переписке разрешено работать и в какой роли |
| ChatLocation | `config/chat-locations.json` | постоянная, несемантическая | по какому адресу открыть эту переписку |
| ProfileSession | `runtime/profile-sessions/<id>/` | исполнение | эта задача сейчас запущена |
| Endpoint | `runtime/browser-endpoints.json` | присутствие | какие вкладки сейчас на связи |

Помимо ядра оркестрации в модели есть управляющая плоскость и подсистема
артефактов:

| Слой | Сущности |
|---|---|
| Оркестрация | Profile, Binding, ChatLocation, ProfileSession, Endpoint |
| Управление | ProfileActivation |
| Артефакты | ProfileFileStore |

Число сущностей догмой не является: границы слоёв важнее счёта.

Четыре понятия, которые нигде не сливаются в одно поле:

```
profile.enabled                    право пользоваться профилем
activation.effectiveDesiredState   задача должна работать
session.state                      фактическое runtime-состояние
endpoint.available                 браузерная точка доступна
```

Слияние любых двух из них — источник всех дефектов, разобранных в 4.4.0.

## 4. Закрытые решения

### 4.1. ChatLocation отдельно от Binding

Наблюдаемый адрес не пишется в привязку. Иначе смена адреса провайдером
выглядела бы как правка конфигурации и сдвигала дайджест, зафиксированный в Run.

```
config/chat-locations.json
  bindingId, launchUrl, lastObservedAt
```

Адрес обновляется только когда идентичность наблюдаемой вкладки совпала с
привязкой. Изменение этого файла не меняет ни ревизию привязок, ни провенанс Run.
Хранение постоянное, а не runtime: адрес нужен именно тогда, когда ни одной
вкладки нет.

### 4.2. Снимок профиля при запуске

Одной ревизии недостаточно: файлы промптов перезаписываются, и продолжать
исполнение по старой редакции стало бы нечем. При запуске замораживается
содержимое:

```
runtime/profile-sessions/<sessionId>/
  session.json    profileId, profileRevision, profileDigest, snapshotDigest
```

Копии внутри каталога сессии нет: содержимое лежит в общем хранилище снимков,
описанном в 4.2a, и сессия хранит только ссылку.

Снимок неизменяем. Значения секретов в него **не копируются** — только ссылки;
разрешение идёт из `config/secrets/` в момент использования, иначе каталог
сессии станет вторым хранилищем секретов с иными правами.

Правка профиля при запущенной сессии не подхватывается. Интерфейс показывает
расхождение и предлагает перезапуск:

```
Запущено: revision 7 · Текущее: revision 9 · [Перезапустить]
```

При этом `profile.enabled` остаётся живым шлюзом: выключение профиля лишает
запущенную сессию права действовать, не уничтожая её.

### 4.2a. Снимок исполнения Run

Снимка сессии недостаточно. Run может быть создан без сессии, может пережить свою
сессию и продолжать локальное исполнение после её остановки. Если замороженная
конфигурация лежит только в каталоге сессии, то после его уборки живой Run
останется без промптов, определений директив и собственных таймаутов.

Поэтому снимков два, с разным временем жизни:

| Снимок | Что фиксирует | Живёт |
|---|---|---|
| снимок сессии | конфигурацию работающей задачи | пока существует сессия |
| снимок исполнения Run | конфигурацию, по которой исполняется Run | пока существует Run |

Создание снимка Run:

```
Run пришёл в сессии X   создаётся из неизменяемого снимка X, дайджесты совпадают
Run без сессии          создаётся из текущего профиля
в обоих случаях         только ссылки на секреты, значений нет
```

Хранение общее и адресуемое по содержимому: копировать промпты в каждый Run
нельзя, при сотнях Run одной редакции это сотни одинаковых копий.

```
storage/profile-snapshots/<snapshotDigest>/
  snapshot.json
  prompts/base.md
  prompts/roles/<role>.md

data/<runId>/profile-context.json
  profileId, profileRevision, profileDigest, snapshotDigest, sessionId | null
```

Все Run одной редакции делят одну копию, а уборка каталога сессии ничего не
ломает, потому что снимок ей не принадлежит. Снимок сессии ссылается на тот же
объект.

Два дайджеста различаются и не взаимозаменяемы:

```
profileDigest    дайджест семантической конфигурации профиля
snapshotDigest   дайджест точных байтов всего снимка:
                 конфигурация, промпты, директивы, переменные,
                 операционные параметры, ссылки на секреты
```

Run фиксирует оба, а правило 5.3 сравнивает именно `snapshotDigest`. Два профиля
могут иметь одинаковый `profile.json` и разные байты промптов; переносить такой
Run под новую сессию как семантически идентичный нельзя.

Публикация снимка атомарна: временный каталог, запись всех файлов, вычисление
дайджеста, проверка содержимого, атомарное переименование в хранилище, и только
затем запись ссылки в Run или сессию. Состояния «ссылка уже есть, каталог заполнен
наполовину» не существует.

Замороженными для Run оказываются `files.attentionTimeoutSeconds`,
`delivery.endpointWaitTimeoutSeconds`, определения директив, правила ошибок,
промпты и переменные.

Это же делает правило 5.3 точнее: сравниваются дайджест снимка Run и дайджест
снимка новой сессии. При совпадении действие уходит под новой сессией, но Run не
начинает читать её снимок — новая сессия даёт ему маршрут, а не семантику.

### 4.3. Аренды на включение вкладки

Включение вкладки перестаёт быть булевым флагом и получает причины:

```
manual
profile-session:<sessionId>

tabEnabled = manual OR (аренд сессий больше нуля)
```

Запуск добавляет свою аренду, остановка снимает только свою. Вкладка,
включённая оператором вручную, остановкой задачи не гасится. Это же решает
случай, когда одной вкладкой пользуются две задачи.

### 4.4. Состав сессии фиксируется на старте

Набор `bindingId` определяется при запуске. Сама привязка проверяется живьём как
авторизация.

| Событие | Поведение |
|---|---|
| привязка выключена или удалена | чат сессии становится `REVOKED`, действия туда не идут |
| привязка снова включена с той же ролью, профилем и перепиской | восстанавливается автоматически |
| привязка переписана на другую роль, профиль или переписку | `CONFIG_CHANGED`, нужен перезапуск этого чата |
| в профиль добавлена новая привязка | в запущенную сессию не входит, нужен перезапуск |

Редактирование конфигурации не меняет топологию работающей задачи молча.

### 4.5. Остановка

```
новые действия запрещены
ожидающие действия этой сессии отменяются как SESSION_STOPPED
аренды включения снимаются
вкладки не закрываются
```

Отмена ожидающих обязательна: иначе сообщение, поставленное в очередь два дня
назад, ушло бы при следующем запуске. Закрытие вкладок — отдельное явное
действие оператора, не часть остановки.

Уже принятый Run продолжает локальное исполнение после остановки: см. 5.1.

### 4.6. Разрыв связи и деградация

`DEGRADED` не блокирует задачу. Работа идёт с теми чатами, что онлайн. Действие,
адресованное отсутствующей роли, ждёт со своим таймаутом и падает само, не роняя
сессию.

Два состояния различаются и лечатся по-разному:

| Состояние | Значение | Поведение |
|---|---|---|
| `OPEN_TIMEOUT` | вкладка создана, endpoint с ожидаемой идентичностью не появился | `CHAT_UNRESPONSIVE`, сессия `DEGRADED` |
| `OFFLINE` | endpoint существовал и временно пропал | ожидание восстановления, перезапуск не нужен |

### 4.7. Время жизни `endpointId`

Идентифицирует время жизни конкретной вкладки: переживает перезагрузку и
переход внутри вкладки, не переживает её закрытие.

```
перезагрузка              endpointId тот же
переход A → B             endpointId тот же, идентичность переписки изменилась
закрытие и открытие       новый endpointId
```

Постоянным идентификатором машины или браузера он не становится.

### 4.8. Выбор вкладки при запуске

Алгоритм, а не формулировка:

```
1. endpointId уже принадлежит этой сессии
2. endpoint явно выбран оператором для этой сессии
3. подходящий endpoint ровно один
4. вкладка создана этим запуском и она одна
5. иначе ENDPOINT_AMBIGUOUS, спрашиваем оператора
```

Привязанность сессии к `endpointId` переживает `OFFLINE`. Повторный выбор
разрешён только когда она явно сброшена, endpoint перешёл в `CLOSED` или
`EXPIRED`, либо оператор выбрал другую вкладку. Иначе при кратком офлайне система
перескочила бы на вторую вкладку той же переписки лишь потому, что сейчас она
единственная на связи.

Выбора по наименьшему номеру вкладки или «первого попавшегося» нет ни на одной
ступени.

## 5. Решения по жизненному циклу Run и сессии

### 5.1. Вход при остановленной сессии — решено

`ProfileSession.state` не является шлюзом авторизации входящего исполнения.
Сессия управляет оркестрацией и своими арендами, а не заменяет конфигурационную
авторизацию.

Вход проверяется живьём по включённому профилю, существующей и включённой
привязке, совпадению идентичности и действующему состоянию включения вкладки.

Аренды из 4.3 дают нужное поведение без отдельного входного шлюза:

```
вкладка включена только арендой сессии
  остановка снимает аренду, вкладка выключается, вход прекращается сам

вкладка включена оператором вручную
  остановка снимает только свою аренду, ручная остаётся, вход работает
```

Следствия:

- уже принятый Run может продолжать локальное исполнение после остановки;
- выключение профиля остаётся административным жёстким стопом и закрывает
  живой шлюз в том числе для ранее принятых Run;
- остановка запрещает новые исходящие действия своей сессии и отменяет её
  ожидающие действия как `SESSION_STOPPED`, но сам Run не отзывает;
- допустим Run без сессии: если активной сессии нет, а вкладка включена
  вручную, Run принимается с `sessionId = null`. Это штатная сущность, а не
  пережиток совместимости. Его исходящие действия разрешаются обычным
  резолвером endpoint и не отменяются ничьей остановкой.

Провенанс Run дополняется необязательными полями:

```
sessionId              | null
sessionProfileRevision | null
sessionProfileDigest   | null
```

Наличие `sessionId` — провенанс, а не пожизненное разрешение.

**Жизненный цикл Run не равен жизненному циклу сессии.**

### 5.2. Восстановление после перезапусков — решено

Отдельного механизма восстановления нет. Оно выполняется тем же примирителем,
который сводит фактическое состояние к активации. Семантика — раздел 9c.

### 5.3. Run, переживший свою сессию — решено

Отменённые при остановке действия не оживают никогда.

Новое исходящее действие старого Run выполняется под текущей сессией только при
совпадении всех пяти: `profileId`, `snapshotDigest`, `bindingId`, роль,
идентичность переписки. При любом расхождении автоматического переноса нет —
оператор получает вопрос с обеими конфигурациями.

Провенанс Run не переписывается:

```
run.sessionId            = X    неизменяемый провенанс
action.deliverySessionId = Y    под чьей сессией ушло действие
```

## 6. Машина состояний ProfileSession

```
                 start
   STOPPED ──────────────▶ STARTING
      ▲                       │
      │                       │ все требуемые чаты ONLINE
      │                       ▼
      │                    RUNNING ◀────────┐
      │                       │             │ чат вернулся
      │   все аренды сняты    │ хотя бы     │
      │                       │ один чат    │
   STOPPING ◀──── stop ───────┤ недоступен  │
                              ▼             │
                          DEGRADED ─────────┘
```

| Состояние | Значение | Что разрешено |
|---|---|---|
| `STOPPED` | задача не работает | ничего от имени сессии; вход и ручная работа не затронуты |
| `STARTING` | снимок сделан, чаты открываются или проверяются | исходящих действий нет |
| `RUNNING` | все требуемые чаты на связи | всё |
| `DEGRADED` | часть чатов недоступна | работа с доступными; действие к недоступной роли ждёт со своим таймаутом |
| `STOPPING` | снятие аренд и отмена ожидающих | новых действий нет |

Переходы:

| Из | В | Условие |
|---|---|---|
| `STOPPED` | `STARTING` | `effectiveDesiredState` стал `ACTIVE`; снимок профиля создан |
| `STARTING` | `RUNNING` | каждый чат состава в `ONLINE` |
| `STARTING` | `DEGRADED` | истёк таймаут открытия хотя бы одного чата |
| `RUNNING` | `DEGRADED` | чат ушёл в `OFFLINE`, `CHAT_UNRESPONSIVE`, `REVOKED` или `CONFIG_CHANGED` |
| `DEGRADED` | `RUNNING` | все чаты снова `ONLINE` |
| любое | `STOPPING` | `effectiveDesiredState` стал `INACTIVE` |
| `STOPPING` | `STOPPED` | аренды сняты, ожидающие отменены |

`DEGRADED` само по себе не ошибка: это сводное состояние неполноты сессии.
Нужно ли вмешательство, определяет состояние конкретного чата:

```
OFFLINE             восстанавливается сам
REVOKED             восстанавливается после возврата допустимой конфигурации
CHAT_UNRESPONSIVE   требует явного повторного открытия
CONFIG_CHANGED      требует перезапуска чата или сессии
```

Выключение профиля не меняет состояние сессии. Оно закрывает живой шлюз, поэтому
сессия остаётся в своём состоянии, но её действия отклоняются как
`PROFILE_DISABLED`. Это разные вещи, и слияние их в одно состояние запрещено
разделом 3.

Приведение к намерению идемпотентно: повторное объявление `ACTIVE` не создаёт
вторую сессию и не пересоздаёт снимок; повторное `INACTIVE` не является ошибкой.

## 7. Машина состояний SessionChat

Состояние отдельного чата внутри сессии. Своё для каждой привязки из состава.

```
   PENDING ──▶ OPENING ──▶ ONLINE ◀──▶ OFFLINE
                  │           │
                  │ таймаут   ├──▶ REVOKED
                  ▼           └──▶ CONFIG_CHANGED
             CHAT_UNRESPONSIVE
```

| Состояние | Значение | Действия туда |
|---|---|---|
| `PENDING` | входит в состав, ещё не рассматривался | нет |
| `OPENING` | вкладка открыта или найдена, ждём пульс с нужной идентичностью | ждут |
| `ONLINE` | endpoint на связи, идентичность совпала | идут |
| `OFFLINE` | был на связи, временно пропал | ждут со своим таймаутом |
| `CHAT_UNRESPONSIVE` | вкладка создана, ожидаемый endpoint так и не появился | падают по таймауту открытия |
| `REVOKED` | привязка выключена или удалена | не идут |
| `CONFIG_CHANGED` | привязка переписана на другую роль, профиль или переписку | не идут, нужен перезапуск чата |

Ключевое различие, которое нельзя стирать:

```
CHAT_UNRESPONSIVE   никогда не был на связи  → таймаут открытия, DEGRADED
OFFLINE             был и пропал             → ожидание, перезапуск не нужен
```

Восстановление:

| Из | В | Условие |
|---|---|---|
| `OFFLINE` | `ONLINE` | пульс с той же идентичностью вернулся; подтверждение не требуется |
| `REVOKED` | `ONLINE` | привязка снова включена с тем же профилем, ролью и перепиской |
| `CHAT_UNRESPONSIVE` | `OPENING` | только по явному действию оператора |
| `CONFIG_CHANGED` | — | только перезапуск чата или сессии |
Расхождение идентичности состоянием чата не является. Если выбранная вкладка ушла
в другую переписку, для чата сессии подходящего endpoint просто нет, и он
переходит в `OFFLINE`.

Конфликт не является и свойством endpoint: одна вкладка может не подходить одной
привязке и идеально подходить другой. Endpoint хранит только наблюдаемую
идентичность, а отказ живёт в отношении «цель ↔ кандидат» и записывается
резолвером:

```
candidate: endpointId
expectedConversationId, observedConversationId
rejectedReason: IDENTITY_MISMATCH
```

Такой кандидат исключается для этой цели и только для неё. Появился подходящий — чат вернулся в
`ONLINE`. Состояние роли не смешивается с дефектом конкретной вкладки.

Механизм устаревания закрепления из 4.4.0 исчезает целиком, вместе с полями
`stale`, `staleReason` и `approvedEndpointId`.

## 8. Желаемое и фактическое состояние задачи

Запуск задачи не привязывается к действию человека. Цель — работа без оператора,
поэтому вводится разделение:

Намерение хранится **отдельно от профиля**. Внутри `profile.json` оно сдвигало бы
ревизию и дайджест при каждом включении задачи, и обычный останов выглядел бы как
правка конфигурации.

```
config/profile-activation.json          постоянное намерение
  profileId
  configIntent:      ACTIVE | INACTIVE
  scheduleIntent:    ACTIVE | INACTIVE | null
  operatorOverride:  ACTIVE | INACTIVE | null
  restartGeneration: монотонное число
  changedAt, changedBy, reason

effectiveDesiredState = operatorOverride ?? scheduleIntent ?? configIntent

runtime/profile-sessions/<id>/          фактическое состояние
```

Три источника не пишут в одно поле: иначе очередной тик расписания отменил бы
ручную остановку. Приоритет и режимы интерфейса описаны в 9c.

Четыре независимые оси:

```
profile.enabled           право пользоваться профилем
activation.effectiveDesiredState   намерение: задача должна работать
session.state             фактическое состояние исполнения
endpoint.available        браузерная точка доступна
```

Система непрерывно сводит фактическое к желаемому: открывает недостающие вкладки,
берёт аренды, восстанавливает после перезапуска браузера. Оператор нажатием
меняет `operatorOverride` либо очищает его, а `effectiveDesiredState` вычисляется
из трёх источников. В автоматическом режиме намерение ставит конфигурация или
расписание, и та же машина состояний из раздела 6 работает без единого нажатия.

`changedBy` фиксирует источник намерения — `operator`, `schedule`, `config`, — а не
имя человека.

**Канал примирения.** Консоль не может обратиться к расширению сама, а без
открытых вкладок канала нет вовсе. Поэтому расширение получает собственный
примиритель: сверка при старте service worker и далее по `chrome.alarms`. Он
читает намерения и приводит к ним аренды и вкладки. Это не быстрый постоянный
опрос — частота задана в 9c, — но без него автономный запуск,
расписание и восстановление после перезапуска браузера невозможны.

Это отменяет формулировки «оператор запускает» в разделах 4.3, 4.4 и 4.5: там,
где написано «запуск», читать «переход желаемого состояния в ACTIVE».

Замечания, требующие решения до реализации.

**Пункт 2 — решено.**

```
файл перечислен в блоке размещения   обязательная зависимость
  не удалось получить                сначала разбор: запрос в чат или оператор
  разбор не состоялся, артефакт есть берётся новейший, подмена помечается
  разбор не состоялся, артефакта нет FILE_ACQUIRE_FAILED, шаг не запускается

файл не перечислен, получали попутно
  не удалось получить                исполнение не блокируется, ошибки нет
```

Во втором случае телеметрию сохраняем, но это не AUTO ERROR и не красная ошибка
Run.

**Материализация.** Когда чат запрашивает, скажем, `/tmp/pap2/tool.tar.gz`, а
объект уже лежит в хранилище, возвращать внутренний путь `objects/<sha256>`
нельзя: это молча изменило бы смысл блока размещения файлов. Резолвер находит
артефакт и **материализует именно запрошенный путь** атомарной копией или ссылкой
внутрь разрешённого корня.

Хранилищу нужен ключ. Имя файла не годится: два профиля легко пришлют разные
`config.json`. Адресация по профилю и хэшу содержимого, исходное имя — атрибут.
Это даёт дедупликацию и делает пункт 4 дешёвым: сохранять нечего, всё уже лежит.

Одно имя внутри профиля может принадлежать нескольким артефактам: тот же файл
приходит в разных Run и меняется между ними. Старые версии не затираются, под
именем живёт список артефактов с временами создания.

Разрешение запроса по имени:

```
1. артефакт, уже закреплённый за этим Run     внутри Run файл неизменен
2. файл, размещённый этим же Run              собственный важнее чужого
3. файл получить не удалось                   FILE_NEEDS_ATTENTION, разбор
4. разобрать не удалось: новейший по имени    запасной путь, подмена помечается
5. брать нечего                               FILE_ACQUIRE_FAILED
```

Ступень 1 делает разрешение однократным: как только файл для Run определён, он
записывается в манифест Run и больше не пересматривается. Повторный шаг получает
те же байты, а не то, что успело появиться в хранилище позже.

Ступень 2 обязана стоять выше ступени 3. Иначе Run, положивший свой `config.json`,
получит чужой — присланный минутой позже другим Run того же профиля. Два
параллельных чата молча портили бы друг другу входные данные.

Ступень 3 — разбор, а не автоматическая подмена. Недоступный файл сначала
выносится наружу, потому что правильный ответ обычно есть и он лучше любой
догадки системы.

Оба пути идут **параллельно, в одном бюджете времени**, а не последовательно:

```
t0 = момент, когда обязательный файл получить не удалось

одновременно:
  запрос файла обратно в исходный чат
  Run попадает в «Требует внимания»; оператор может приложить файл
  либо указать конкретный артефакт

до t0 + profile.files.attentionTimeoutSeconds
  первый валидный результат выигрывает
```

Разделять бюджет на «столько-то чату, потом столько-то оператору» нельзя: это
искусственно удлинило бы ожидание там, где оператор готов вмешаться сразу.

Таймаут задаётся профилем и берётся Run из **его собственного снимка исполнения**.
Run, созданный внутри сессии, получает снимок из снимка этой сессии; Run без
сессии — из снимка, созданного из текущего профиля в момент приёма. Иначе Run без
сессии остался бы без однозначного источника параметра. Конкретное значение по умолчанию выбирается при
реализации; в контракте важен принцип: параметр профиля, заморожен снимком,
отсчитывается от входа в состояние разбора.

Закрепление атомарно. Возможна гонка: оператор выбрал артефакт, а через сто
миллисекунд из чата приехал файл. Побеждает тот, кто закрепился первым; второй
сохраняется в хранилище, но манифест Run не переписывает.

То же и за границей таймаута. Если бюджет истёк, шаг пошёл на подмене, а файл
приехал позже — он сохраняется, но Run не переигрывается. Иначе шаг, уже
исполненный на одних байтах, задним числом оказался бы исполненным на других.
Переигровка возможна только явным действием оператора.

Запрос файла обратно в чат — обычное исходящее действие, а не обход
маршрутизации: он проходит те же шлюзы, что и любая отправка, включая правило
5.3. Если исходная сессия остановлена, запрос уходит под совместимой текущей
сессией либо не уходит вовсе, и тогда остаются ручной путь и подмена.

Ход разбора записывается:

```
fileResolution
  requestedName
  state: NEEDS_ATTENTION | RESOLVED | SUBSTITUTED | FAILED
  resolvedArtifactId
  resolvedBy: source-chat | operator-upload | operator-selection | fallback-latest
  requestedAt, resolvedAt, substituted
```

Эта запись нужна не только интерфейсу: без неё восстановление после перезапуска
консоли не сможет понять, чем закончился разбор.

Ступень 4 — правило «новое важнее старого». Оно включается только когда разбор не
состоялся: запрос к чату не дал файла, оператор не вмешался, таймаут вышел.
Работа продолжается на последней известной версии вместо остановки, и это
осознанный размен: сорванная загрузка вложения случается часто, а полная остановка
из-за неё обходится дороже помеченной подмены.

Подмена обязана быть видимой. Шаг получает байты, которых не запрашивал, поэтому
в Run записывается и показывается:

```
substituted: true
requestedName, artifactId, sourceRunId, createdAt, reason
```

Молчаливой подстановки не бывает: правило меняет поведение, но не скрывает его.

`FILE_ACQUIRE_FAILED` остаётся последней мерой — когда артефакта с таким именем в
профиле нет вовсе.

Выдача файлов, ушедших в чат, идёт по манифесту доставки, а не по текущей
новейшей версии: байты и имена обязаны соответствовать реально отправленным.

**Пункт 3.** Детектор сейчас сообщает только факт срабатывания. Для подсветки
нужны смещения совпадения в выводе, то есть возврат позиций из
`execution_error_detector.py`. Это единственный пункт, требующий правки того
файла.

**Пункт 5.** Место в интерфейсе уже есть — вкладка директив в редакторе профиля,
но она сырой JSON. Раз ты сам её не нашёл, обнаруживаемость уже провалилась: вкладка называется
технически и содержит JSON. Нужна вкладка «Команды» с карточками и кнопкой
добавления, и прямая ссылка на неё из основного интерфейса. Отдельной глобальной
модели команд не заводим — команды принадлежат профилю.

**Пункт 10.** Второй Run не создаётся вовсе — приём делается идемпотентным.
Повтор увеличивает счётчик у существующего Run, попадает в журнал, а интерфейс
сообщает «повтор уже принят как Run X». Так список Run не засоряется, но и
ощущения проигнорированного сообщения не возникает. Для намеренного повтора —
явное действие «Повторить как новый Run».

Ключ дедупликации требует проверки фактов. Стабильного идентификатора сообщения в
разборе **нет**: `content.js` отдаёт `messagePosition`, а `turnId` записан как
`null`. Значит первичным ключом он быть не может без правки расширения. До неё
ключом служит хэш нормализованного разбора, имена и порядок вложений, их хэши,
переписка и привязка, с ограниченным окном дедупликации. Нормализация обязана
исключать метку времени и идентификатор Run, иначе совпадений не будет никогда.

## 9a. Endpoint: наблюдение, оценка, выбор

Три операции разделены, и смешивать их запрещено:

```
observe(endpoint)           только факты браузера
evaluate(target, endpoint)  чистая функция отношения
select(target, candidates)  единственное место политики выбора
```

### Ключ реестра

Реестр адресуется `endpointId`, а не номером вкладки. Номер — текущий локатор
Chrome, он переиспользуется после закрытия. Пульс с новым `endpointId` создаёт
новый endpoint, даже если номер прежний, и никогда не переписывает старый.

Соответствие `tabId → endpointId` хранится в `chrome.storage.local` вместе с
эпохой и действительно только внутри неё. Перезапуск service worker, перезагрузка
страницы и обновление расширения идентичность вкладки не меняют; запуск браузера
даёт новую эпоху, и соответствия прежней недействительны. Обоснование — 10f.

### Наблюдаемые состояния

| Состояние | Значение | Терминальное |
|---|---|---|
| `ONLINE` | пульс свежий | нет |
| `OFFLINE` | пульс просрочен, доказательств закрытия нет | нет |
| `CLOSED` | расширение наблюдало закрытие вкладки | да |
| `EXPIRED` | не вернулся после смены эпохи браузера | да |

`observe` записывает только `endpointId`, `tabId`, `chatType`, `conversationId`,
`projectId`, `url`, `title`, `lastSeenAt`, присутствие и эпоху. Полей
`bindingId`, `expectedConversationId`, `identityConflict`, `approved`, `stale` в
endpoint нет и быть не может.

Сырой URL в оценке идентичности не участвует: он подсказка для запуска. Сравнение
идёт по нормализованным `chatType`, `conversationId` и `projectId` по правилам
провайдера, иначе смена адреса снова начнёт влиять на маршрутизацию.

### Таблица случаев

| Ситуация | `evaluate` | Что делает `select` |
|---|---|---|
| пульс свежий, идентичность совпала | `ELIGIBLE` | кандидат |
| пульс просрочен | `OFFLINE` | сейчас не кандидат |
| другой тип чата | `CHAT_TYPE_MISMATCH` | исключить |
| другая переписка | `IDENTITY_MISMATCH` | исключить |
| проект обязателен и не совпал | `PROJECT_MISMATCH` | исключить |
| время жизни закончено | `DEAD_ENDPOINT` | исключить навсегда |
| ровно один `ELIGIBLE` | — | выбрать |
| ноль кандидатов, выбранный только офлайн | — | `WAITING_FOR_ENDPOINT`, не перевыбирать |
| ноль кандидатов, привязанность закончилась | — | искать заново или открыть вкладку |
| несколько `ELIGIBLE`, привязанности нет | — | `ENDPOINT_AMBIGUOUS` |
| несколько `ELIGIBLE`, один принадлежит сессии | — | использовать его |

### Один управляющий экземпляр

Эпоха браузера различает поколения вкладок, но не различает браузеры. Если с одной
консолью работают два независимых браузера, новая эпоха первого не даёт способа
понять, какие прежние endpoints принадлежали ему, а какие всё ещё живому второму.
Постоянного идентификатора браузера мы намеренно не заводим.

Ограничение 4.5.0: **одна консоль — один управляющий экземпляр расширения**.
Несколько окон и вкладок одного браузера допустимы; несколько независимых
браузеров, одновременно управляющих одной консолью, не поддерживаются.

Обнаружения по пульсу endpoint недостаточно: второй браузер может не иметь ни
одной поддерживаемой вкладки, а его примиритель уже готов их открывать. Поэтому
управляющий агент подаёт собственный пульс, существующий и при нуле endpoint:

```
controlHeartbeat   browserEpoch, extensionVersion, sentAt
```

Сервер держит аренду владения, а не просто множество живых эпох:

```
controlAgent   ownerEpoch, lastSeenAt, leaseUntil
```

| Ситуация | Поведение |
|---|---|
| владельца нет | эпоха получает аренду и план примирения |
| та же эпоха | аренда продлевается |
| другая эпоха, владелец жив | `CONTROL_AGENT_CONFLICT`, план не выдаётся, конфликт показан |
| владелец замолчал, аренда истекла | новая эпоха становится владельцем, endpoints прежней — `EXPIRED` |

Показать нарушение мало: если план получат обе эпохи, мы обнаружим конфликт и
всё равно получим двух конкурирующих примирителей. Не владеющий агент не имеет
права открывать вкладки, брать аренды и вообще менять состояние браузера.

Аренда может истечь не из-за смерти браузера, а из-за задержки пульса — сон
машины, сетевой перебой. Здесь важна граница:

```
аренда истекла, владельцем никто другой не стал, вернулась та же эпоха
  → та же эпоха восстанавливает владение, endpointId не меняются

аренда истекла, другая эпоха успела стать владельцем
  → endpoints прежней эпохи EXPIRED
  → прежний агент, снова получив владение, сбрасывает соответствие
    номеров вкладок и выдаёт новые endpointId
```

Новые идентификаторы нужны именно после реальной передачи владения, а не после
любого истечения аренды. Иначе мигающая аренда без смены владельца заставляла бы
пересоздавать идентичности без причины.

Поддержка нескольких управляющих потребует отдельного идентификатора агента и
политики владения — это не расширение текущего дизайна, а другая задача.

### Жизненный цикл эпохи

```
старт браузера           новая эпоха
перезапуск service worker эпоха сохраняется
перезагрузка страницы    эпоха и endpointId сохраняются
закрытие вкладки         CLOSED, соответствие номера и endpointId удаляется
перезапуск браузера      новая эпоха, незавершённые endpoints прежней EXPIRED
```

### Терминальность и поздний пульс

`CLOSED` и `EXPIRED` терминальны для конкретного `endpointId`. Возможна гонка:
пульс отправлен, вкладку закрыли, событие закрытия дошло первым, пульс — позже.

```
CLOSED  + пульс того же endpointId   игнорируется
EXPIRED + пульс того же endpointId   игнорируется
```

Переходов `CLOSED → ONLINE` и `EXPIRED → ONLINE` не существует. Появившаяся заново
вкладка обязана иметь новый `endpointId`.

### Данные, которые сообщает расширение

```
heartbeat   endpointId, browserEpoch, tabId, chatType,
            conversationId, projectId, url, title
tabClosed   endpointId, browserEpoch, tabId
```

Событие закрытия одновременно удаляет локальное соответствие номера вкладки и
`endpointId`, иначе переиспользованный номер унаследовал бы чужую идентичность.

### Срез 2 как граница совместимости

Привязанность освобождают только `CLOSED` и `EXPIRED`, а оба требуют изменений
расширения. Поэтому серверная семантика привязанности и изменения расширения
устанавливаются и принимаются **вместе**, одним срезом:

```
сервер      реестр по endpointId, CLOSED и EXPIRED, привязанность
расширение  endpointId, эпоха, событие закрытия, аренды
```

Срез 1 маршрутизацию не меняет, поэтому до полного среза 2 действует прежняя
маршрутизация 4.4.0. Промежуточное ограничение остаётся в документе для разработки
и отката, но в рабочий выкат частями не попадает.

### Строки приёмки

Каждая проверяется тестом:

```
перезагрузка страницы сохраняет endpointId
поздний пульс после CLOSED не воскрешает endpoint
поздний пульс прежней эпохи после EXPIRED не воскрешает endpoint
просрочка аренды без смены владельца не меняет endpointId
смена владельца делает endpointId прежней эпохи невосстановимыми
разрыв пульса не меняет выбранный endpoint
возвращение той же вкладки восстанавливает ONLINE
переход в другую переписку исключает endpoint только для старой цели
закрытие вкладки завершает привязанность
переиспользованный номер вкладки не наследует прежний endpointId
несколько подходящих вкладок не выбираются молча
```

## 9b. ChatLocation

Адрес нужен, чтобы открыть переписку, когда ни одной вкладки нет. Четыре правила:

1. Запись обновляется только при совпадении идентичности, то есть когда
   `evaluate` вернул `ELIGIBLE`. Наблюдение чужой вкладки адрес не трогает.
2. Адрес никогда не участвует в выборе endpoint. Идентичность сравнивается по
   нормализованным `chatType`, `conversationId` и `projectId`.
3. Устаревший адрес при неудачном открытии не перезаписывается ничем угаданным.
   Не открылось — остаётся прежний адрес и состояние `CHAT_UNRESPONSIVE`.
4. Успешно появившийся после открытия endpoint атомарно подтверждает или обновляет
   запись.

```
config/chat-locations.json
  bindingId, launchUrl, lastObservedAt
```

Изменение файла не меняет ни ревизию привязок, ни провенанс Run.

## 9c. Активация и примиритель

### Три источника намерения

Одно поле, в которое пишут трое, даёт самопроизвольную отмену: оператор остановил
задачу, а очередной тик расписания вернул её. Поэтому источники раздельны:

```
ProfileActivation
  configIntent:      ACTIVE | INACTIVE
  scheduleIntent:    ACTIVE | INACTIVE | null
  operatorOverride:  ACTIVE | INACTIVE | null
  restartGeneration: <монотонное число>

effectiveDesiredState = operatorOverride ?? scheduleIntent ?? configIntent
```

В интерфейсе это режим: «Автоматически», «Запущено», «Остановлено».
«Автоматически» очищает переопределение оператора и возвращает управление
расписанию и конфигурации. Ручная остановка держится, пока оператор сам не вернёт
автоматический режим.

### Перезапуск

Правка профиля запущенную задачу не перезапускает — это решено. Но и
`effectiveDesiredState` равное `ACTIVE` само по себе не сообщает примирителю о
нажатии «перезапустить с новой
конфигурацией», а искусственное переключение в `INACTIVE` и обратно ломается при
управлении расписанием. Поэтому отдельный монотонный счётчик:

```
activation.restartGeneration != session.restartGeneration  →  перезапуск задачи
revision профиля изменился, generation тот же              →  сессия живёт снимком
```

### Частота

```
reconcileIntervalSeconds  30
controlAgentLeaseSeconds  90
```

Это системные настройки, не параметры профиля и не часть снимка: частота
примирения не меняет семантику Run или сессии.

Периодический сигнал — страховочная сетка. Немедленное примирение вызывают: старт
service worker, старт браузерной сессии, изменение активации через интерфейс или API, закрытие
вкладки, явный перезапуск. Изменение намерения расписанием без активного канала
обнаруживается максимум за один период.

### Восстановление

Отдельного механизма не требуется: восстановление и есть примирение.

| Событие | Поведение |
|---|---|
| перезапуск консоли | читает активацию, сессии и сохранённые разборы файлов; новых сессий из-за рестарта не создаёт; ждёт управляющего агента |
| перезапуск service worker | эпоха та же, сразу пульс, план получается заново; аренды восстанавливаются из консоли, а не из памяти worker |
| перезапуск браузера | новая эпоха, получение владения, прежняя объявляется `EXPIRED` |

Порядок при перезапуске браузера важен: сначала обнаружить вкладки, которые Chrome
восстановил сам, выдать им новые `endpointId`, сопоставить через `evaluate` и
`select`, и только потом открывать реально недостающие. Иначе примиритель успеет
открыть дубли прежде, чем увидит восстановленное.

Сессия не получает новый идентификатор из-за перезапуска процесса или браузера:
пока намерение `ACTIVE` и сохранённая сессия корректна, восстанавливается та же
сессия с тем же `snapshotDigest`. Новая создаётся только после настоящего перехода
жизненного цикла или явного перезапуска.

## 9d. ProfileFileStore

Пять слоёв с разными обязанностями. Смешивать их запрещено так же, как
`observe`, `evaluate` и `select`.

### 1. Физическое хранение

```
storage/profile-files/<profileId>/
  objects/<sha256>
  metadata/<artifactId>.json
```

Публикация атомарна, как у снимков:

```
получить во временный файл → посчитать sha256 и размер → проверить ограничения
→ атомарно опубликовать объект → атомарно создать запись
→ только после этого Run вправе ссылаться на артефакт
```

Иначе после аварии останется запись, указывающая на недописанные байты.

### 2. Записи артефактов

```
artifactId, profileId, sha256, size, originalName, createdAt
source
  kind: incoming-attachment | command-put-files | result-file
        | operator-upload | recovered-from-chat
  runId | bindingId | conversationId
```

`artifactId` — идентичность записи и происхождения, `sha256` — идентичность байтов.
Это разные вещи: одинаковые байты могли прийти в разные Run, под разными именами
и из разных источников, поэтому один объект может иметь несколько записей.

Правило «новейший по имени» сортирует **записи**, а не объекты.

### 3. Манифест файлов Run

Запрошенное и разрешённое разделены:

```
requestedName, requestedPath
resolution
  state: NEEDS_ATTENTION | RESOLVED | SUBSTITUTED | FAILED
  artifactId, resolvedBy, substituted
  requestedAt, deadlineAt, resolvedAt
```

`deadlineAt` записывается в момент перехода в разбор, а не пересчитывается из
`requestedAt` и таймаута при каждом чтении. Это упрощает восстановление после
рестарта и делает поведение во времени проверяемым.

### 4. Получение и материализация

Объект хранилища неизменяем, а команда может изменить файл, который получила.
Поэтому базовая семантика — **копия**, а не жёсткая ссылка:

```
объект хранилища → копия в запрошенный путь → команда работает с копией
```

Запрошенный путь проходит проверку до материализации:

```
нормализовать путь
→ убедиться, что результат внутри workDir или tempDir из снимка исполнения Run
→ запретить выход через .. и переход по символическим ссылкам
→ только затем материализовать
```

Без неё корректное хранилище обходится строкой назначения, и подсистема запишет
файл туда, куда профилю писать не разрешено.

Reflink допустим там, где файловая система гарантирует копирование при записи.
Обычная жёсткая ссылка недопустима: правка `/tmp/pap2/config.json` изменила бы сам
объект и уничтожила содержимое хранилища для этого хэша.

Существующий путь назначения не перетирается безусловно:

| Состояние пути | Поведение |
|---|---|
| отсутствует | материализовать |
| существует, `sha256` совпадает | идемпотентно, ничего не делать |
| существует, отличается | `FILE_DESTINATION_CONFLICT`, не перезаписывать |

Иначе повторное примирение после рестарта уничтожило бы файл, который предыдущий
шаг уже успел изменить.

### 5. Манифест отправленных вложений

Фиксируется **до** передачи расширению и после этого не пересчитывается, даже если
в хранилище появился более новый артефакт с тем же именем:

```
deliveryId
attachments: ordinal, artifactId, sha256, outgoingFilename, size
```

Именно он обслуживает выгрузку файлов в том виде, в каком они ушли в чат.

### Строки приёмки

```
два артефакта с одинаковыми байтами и разным происхождением делят один объект,
  но остаются двумя записями
изменение материализованного файла шагом не меняет объект в хранилище
повторная материализация в неизменившийся путь идемпотентна
изменённый путь назначения не перезаписывается молча
манифест доставки не меняется от появления более нового артефакта
запись артефакта не появляется раньше опубликованного объекта
```

## 9e. Разрешение цели chat.send

Ничего нового здесь не изобретается: это сборка принятых решений в один
детерминированный конвейер.

```
цель действия
  → привязка и роль
  → живая авторизация: профиль включён, привязка существует и включена,
    привязка соответствует зафиксированной топологии
  → сессия доставки: исходная действительна,
    либо совместимая текущая по правилу 5.3, либо маршрут без сессии
  → чат сессии и идентичность цели
  → привязанность сессии к endpoint
  → evaluate(цель, endpoints)
  → select(цель, кандидаты)
```

| Исход | Поведение |
|---|---|
| `ONLINE` | манифест доставки фиксируется, отправка идёт |
| офлайн при живой привязанности | `WAITING_FOR_ENDPOINT`, таймаут из снимка Run |
| `CLOSED` или `EXPIRED` | привязанность освобождена, выбор заново или открытие вкладки |
| несколько кандидатов | `ENDPOINT_AMBIGUOUS`, вопрос оператору, молчаливого выбора нет |
| авторизация не прошла | терминальная ошибка авторизации |

Два ожидания различаются и не сливаются:

```
WAITING_FOR_ENDPOINT   маршрут известен, точка временно недоступна  → восстановится само
ENDPOINT_AMBIGUOUS     маршрут нельзя выбрать безопасно             → не восстановится
```

Первое разрешается возвращением вкладки. Второе не разрешается ничем из
перечисленного:

```
временем
таймаутом пульса
временным офлайном одного из кандидатов
порядком номеров вкладок
появлением «сейчас единственного онлайн»
```

Повторный выбор допустим только после явного выбора оператора либо после
структурного исчезновения неоднозначности: кандидат перешёл в `CLOSED` или
`EXPIRED`, либо перестал соответствовать идентичности или конфигурации. Если
после такого изменения остался ровно один подходящий, действие продолжается
само.

Смешивать эти два ожидания нельзя: краткий сетевой сбой не должен превращать
неоднозначность в молчаливый выбор, но и навсегда закрытая вторая вкладка не
должна держать действие заблокированным до прихода человека.

Таймаут ожидания берётся из снимка исполнения Run, а не из текущего профиля и не
из снимка сессии — Run может её пережить.

Резолвер становится одним из исполнителей конвейера действий, а не особым кодом
внутри разбора или исполнителя.

## 9f. Директивы и конвейер действий

Раздел начинается с контракта действия, а не со списка директив: иначе частные
случаи снова просочатся в разбор.

```
сырая директива
  → разбор
  → нормализованная директива
  → проверка по снимку профиля
  → однократная компиляция
  → сохранённый граф действий
  → исполнитель действий
  → обработчик по типу
```

**Разбор ничего не исполняет.** Он распознаёт структуру. Компилятор один раз
превращает её в неизменяемые действия, а ожидание, восстановление, маршрутизация
и побочные эффекты живут дальше в конвейере.

### Действие

Определение и состояние разделены физически, см. 9g.

`actionId` стабилен после построения плана. После рестарта консоль не
компилирует директивы заново и не порождает новые действия — она читает
сохранённый граф и продолжает его.

### Идемпотентность побочных эффектов

```
первый запуск A17   создаёт доставку D42, фиксирует манифест вложений
рестарт во время отправки
повтор A17          использует ту же D42, новой доставки и манифеста не создаёт
```

Ключ даёт одинаковую идентичность попытки, но **однократности внешнего эффекта
он не даёт**: у веб-чата нет способа подтвердить, что доставка уже исполнена.
Границу закрывает журнал доставки и состояние `OUTCOME_UNKNOWN`, см. 9g.

### Состояния

```
PENDING  READY  RUNNING
WAITING_FOR_ENDPOINT   ENDPOINT_AMBIGUOUS   FILE_NEEDS_ATTENTION
OUTCOME_UNKNOWN
SUCCEEDED  FAILED  CANCELED
```

Причины ожидания в сохранённом состоянии остаются различимыми. Именно они
определяют, кто имеет право вывести действие из ожидания: время, система или
оператор. Общий класс ожидания допустим в интерфейсе, но не в хранимом состоянии.

### Зеркальные отправки и восстановление файлов

Дублирование файлов запроса и результата не прячется внутрь отправки. Команда
компилируется в явные действия:

```
primary chat.send
mirror chat.send  parentActionId, attachmentPolicy
```

У каждой зеркальной доставки свой идентификатор, своё разрешение цели, свой
результат и свой след в журнале. Основная отправка не становится скрыто зависимой
от зеркальной; ошибка зеркала видна, но по умолчанию не роняет основную.

Автоматический запрос недостающего файла обратно в чат — тоже не особая ветка
хранилища, а обычное дочернее действие отправки с теми же правилами авторизации и
выбора endpoint из 9e.

### Что это позволяет удалить

Здесь и только здесь удаляются `CONTROL_TYPES`, `_handle_control` и особый случай
завершения разработки — потому что появляется механизм, который делает их работу
не набором новых `if`, а конфигурацией профиля.

## 9g. Схемы плана и состояния

### Граф зависимостей отдельно от происхождения

```
ActionDefinition   actionId, parentActionId | null, kind,
                   input, target, attachmentPolicy, timeoutPolicy, errorPolicy
ActionDependency   fromActionId, toActionId, condition
```

`parentActionId` — происхождение: для журнала, интерфейса и разбора. Порядок
исполнения задают только рёбра зависимостей, и именно они переводят действие из
`PENDING` в `READY`.

```
parentActionId ≠ зависимость исполнения
```

Иначе исполнитель начнёт выводить порядок скрытыми правилами по типу действия, и
особые случаи вернутся уровнем ниже — ровно то, ради устранения чего писался 9f.

### Физическое разделение

```
plan.json    определения действий, рёбра зависимостей, неизменяемый провенанс
state.json   actionId, state, attempt, startedAt, finishedAt,
             sideEffectKey, deliverySessionId, разрешённая цель,
             blockDetail, result, error
```

Поля `waitingReason` нет: состояние уже различает `WAITING_FOR_ENDPOINT`,
`ENDPOINT_AMBIGUOUS`, `FILE_NEEDS_ATTENTION` и `OUTCOME_UNKNOWN`. Второй источник
истины либо дублирует состояние, либо однажды начнёт ему противоречить.
Подробности живут в `blockDetail`: кандидаты, `endpointId`, `deadlineAt`,
запрошенный файл.

`sideEffectKey` создаётся и атомарно сохраняется **до первого внешнего вызова** и
после этого не меняется в пределах данной попытки.

### Окно фиксации внешнего эффекта

Ключ идемпотентности не даёт однократности неидемпотентному эффекту в браузере.
Поэтому расширение ведёт сохраняемый журнал доставки:

```
PREPARED → DISPATCHING → SENT
```

`DISPATCHING` записывается **до** фактической отправки, `SENT` — после
подтверждённой.

| Состояние при восстановлении | Поведение |
|---|---|
| `SENT` | повторно не отправлять, вернуть подтверждение |
| `PREPARED` | отправку можно безопасно продолжить |
| `DISPATCHING` | `OUTCOME_UNKNOWN`, автоматически не повторять |

Последняя строка принципиальна: `DISPATCHING` одинаково означает и «упали за
миллисекунду до отправки», и «упали за миллисекунду после». Надёжно различить их
без идемпотентного API провайдера нельзя, а выбор между возможным пропуском и
возможным дублем молча делать недопустимо — это тот же принцип, что и с
неоднозначностью маршрута.

`OUTCOME_UNKNOWN` сам не возобновляется. Оператор получает два явных действия:
считать отправленным либо отправить заново. Второе — осознанная новая попытка
фиксации с новым ключом, а не скрытый повтор старого неизвестного эффекта.

Журнал доставки переживает перезапуск не только service worker, но и браузера,
поэтому его время жизни **не связано** с `endpointId` и эпохой: это другой класс
сохраняемого состояния.

### Что это даёт

```
неизменяемый план   определения, граф, провенанс
изменяемое состояние  позиция исполнения, ожидания, разрешения, эффекты, результаты
внешний эффект      сохраняемая идентичность попытки
                    плюс явный OUTCOME_UNKNOWN для неразрешимого окна фиксации
```

Утверждение «после рестарта граф не компилируется заново, а продолжается»
становится не принципом, а форматом данных.

## 10. Срезы выката

Вертикальные, не по компонентам. Каждый проверяется и откатывается сам по себе,
не требуя установки следующего.

| Срез | Содержание |
|---|---|
| 1 | схемы, ProfileSession, снимок профиля; вкладки не открываются |
| 2 | `endpointId` и аренды включения в расширении |
| 3a | ChatLocation, запуск и остановка задачи, физическое хранилище файлов, записи артефактов, приём вложений, API и обзор файлов |
| 3b | лестница разрешения файлов, подмена, материализация, конфликт назначения — вместе со срезом 5 |
| 4 | разрешение цели `chat.send` с учётом сессии |
| 5 | generic-директивы, action pipeline, новые схемы плана и состояния |
| 6 | retention Run |
| 7 | уборка: удаление переходного кода и временных полей |

Retention намеренно вынесен отдельным срезом: у него свои риски и он не связан с
маршрутизацией и состоянием сессий.

## 10a. Сборка снимков

Три уборки независимы и не смешиваются:

```
retention Run        удаляет Run по своим правилам
уборка сессий        удаляет runtime-каталоги сессий по своим правилам
сборка снимков       удаляет только недостижимые снимки
```

Снимок удаляется, только если на него не ссылается ни один существующий Run и ни
одна существующая сессия. Существующий — это любой Run в `data/`, а не только
исполняющийся: завершённый остаётся доступен оператору, и без снимка его провенанс
станет невоспроизводимым. Речь при этом только о Run новой схемы — старых после
выката не остаётся.

```
MARK    прочитать существующие Run и существующие сессии
        собрать множество достижимых snapshotDigest
SWEEP   снимок вне множества и старше отсрочки → удалить
```

Счётчик ссылок источником истины быть не может: авария между созданием Run и
инкрементом рассинхронизирует его безвозвратно. Как индекс или телеметрия он
допустим.

Отсрочка отсчитывается **от создания снимка**, а не от обнаружения
недостижимости. Иначе снимок, опубликованный после фазы MARK и получивший ссылку
после начала SWEEP, окажется недостижимым по устаревшему множеству и будет удалён
из-под живого Run.

Возраст сам по себе основанием для удаления не является никогда: он удалит снимок,
на который всё ещё ссылается существующий Run. Соблазн заменить достижимость
удалением каталогов по времени велик и ломает работающую систему незаметно.

## 10b. Проверка раскладки по коду

Раскладка срезов проверена по фактическому r7, а не выведена рассуждением.

Размещение файлов обрабатывает `executor.py`, функция `_execute_put_files`: она
выбирает источник, проверяет путь, копирует и считает хэши, а источником служит
только каталог файлов текущего Run. Следовательно лестница разрешения, подмена,
материализация с проверкой границ и конфликт назначения без правки этого файла не
подключаются.

По инварианту 6 `executor.py` меняется только в ломающем срезе. Поэтому срез 3
разделён:

```
3a  хранилище, записи артефактов, приём вложений, API, обзор файлов
    правок executor.py и protocol_engine.py нет
3b  разрешение, подмена, материализация, конфликт назначения
    выкатывается вместе со срезом 5
```

Два правила уже существуют в r7 в зачаточном виде: существующий путь назначения не
перетирается без явного флага, а источником может быть только каталог своего Run.
То есть 3b обобщает имеющееся поведение, а не вводит новое.

### Форма записи точки врезки

Номера строк сами по себе ссылкой не являются: файл сдвинется, и правка попадёт не
туда. Каждая точка записывается так:

```
срез, релиз-основание, файл, sha256 файла-основания,
символ или функция, диапазон строк,
текущая обязанность, обязанность в 4.5,
тип изменения: добавление | замена | удаление,
что менять нельзя, случаи приёмки
```

Хэш и имя символа не дают применить правку к уже изменившемуся файлу.

Инвентаризация r7 и 2.11.6 выполняется **до** окончательных разделов про
изменения расширения, API, интерфейса и шлюзов: фактический код покажет, где
сейчас живут пульс, состояние включения вкладки, опрос доставки, разрешение цели,
разбор, `CONTROL_TYPES`, получение файлов и проверки авторизации.

## 10e. Следствия инвентаризации

### Манифест требует правки

```
permissions: storage, activeTab, tabs, scripting, downloads
background:  service_worker: background.js
```

Разрешения `alarms` нет. Значит примиритель из 9c требует изменения
`manifest.json`, а не только кода. Это установленный факт, а не предположение:
файл прочитан, версия основания 2.11.6.

### Эпоха: три разных события

```
chrome.runtime.onStartup    новая браузерная сессия  → новая эпоха
перезапуск service worker   та же сессия             → эпоха сохраняется
chrome.runtime.onInstalled  обновление расширения    → эпоха сохраняется,
                                                       если сессия та же
```

Объединять их одной инициализацией нельзя. Иначе обычное обновление расширения
станет фиктивным перезапуском браузера: сервер объявит живые endpoints `EXPIRED`,
и сессии начнут переассоциировать вкладки без причины.

### Явный признак вида опроса

Вид опроса определяется полем, а не выводится из отсутствия номера вкладки:

```
pollKind: ENDPOINT | CONTROL_AGENT
```

Для `ENDPOINT` допустимы пульс вкладки и выдача доставки этому endpoint. Для
`CONTROL_AGENT` — аренда владения и план примирения. Управляющий агент не должен
случайно получить обычную доставку лишь потому, что использует тот же адрес; для
конфликтующей второй эпохи это критично.

### Время жизни причин включения

```
manual
  принадлежит времени жизни конкретной вкладки
  переживает перезапуск service worker
  через перезапуск браузера автоматически не переносится

profile-session:<sessionId>
  восстанавливается примирителем из состояния консоли
  от памяти service worker не зависит
```

Различие не в месте хранения, а в источнике истины:

```
manual              истина — состояние вкладки в расширении
profile-session:*   истина — консоль; локальная запись только кэш
```

Сессионную аренду кэшировать в `chrome.storage.session` можно; считать этот кэш
авторитетным и восстанавливать из него сессию — нельзя. После перезапуска браузера
он исчезает, и это нормально: примиритель восстановит аренду из консоли. У ручной
причины внешней истины нет, поэтому её исчезновение вместе со временем жизни
вкладки тоже нормально.

Попытка сохранить ручную причину по прежнему номеру вкладки опаснее потери: номер
переиспользуется. Автоматический перенос ручной причины на новую вкладку без
отдельного правила идентичности не допускается.

### Что защищает нынешнее вытеснение

`supersede_older_jobs_for_tab:1034` помечает `SUPERSEDED` все нетерминальные
задания, чья цель указывает на тот же номер вкладки, кроме сохраняемого.

Инвариант: **у одной точки доставки не должно быть двух конкурирующих
незавершённых заданий**. Иначе вкладка заберёт устаревшее задание и вставит в чат
неактуальные файлы.

Новый ключ — не просто «переписка вместо номера вкладки». Две последовательные
законные отправки в одну переписку не должны вытеснять друг друга. Инвариант
воспроизводится через идентичность действия и доставки: вытесняется предыдущая
незавершённая попытка **той же логической доставки**, а не всё, что адресовано той
же переписке. Точная формулировка ключа — в точке врезки среза 4.

### Незавершённые задания прежних схем

Правила для них не требуется: при входе в ломающий срез `data/` очищается целиком,
и задания прежних схем исчезают вместе со своими Run. Классифицировать нечего.

`OUTCOME_UNKNOWN` остаётся полностью нужным, но только для аварий **после**
появления журнала доставки, а не как средство спасения данных переходных срезов.

## 10f. Хранение состояния расширения — решено

`chrome.storage.session` держится в памяти на время браузерной сессии, не пишется
на диск и очищается при остановке браузера. Перезапуск service worker он
переживает. Поведение при обновлении и перезагрузке самого расширения
документацией, которую удалось проверить, однозначно не описано.

Разрешать эту неоднозначность не требуется: выбранное хранение корректно при любом
из вариантов.

```
browserEpoch
соответствие tabId → endpointId
состояние ручной причины включения

  → chrome.storage.local, все записи привязаны к текущей browserEpoch
```

`storage.local` не превращается в постоянную идентичность браузера, потому что
записи действительны только внутри своей эпохи. Со следующим запуском браузера
эпоха меняется, и прежние соответствия становятся недействительными.

Время жизни задают события, а не хранилище:

| Событие | Поведение |
|---|---|
| перезапуск service worker | ничего не меняется |
| перезагрузка или обновление расширения | эпоха и соответствия сохраняются |
| `chrome.runtime.onStartup` | новая эпоха, состояние прежней инвалидируется |
| `chrome.tabs.onRemoved` | `CLOSED`, удаление соответствия и ручной причины этой вкладки |

Сессионные причины включения остаются кэшем: их можно держать там же с привязкой к
эпохе, но после перезапуска браузера примиритель строит их заново из консоли.
Ручную причину извне восстановить нельзя, поэтому она живёт, пока жива вкладка.

Журнал доставки хранится там же, но в отдельном пространстве имён и **не
привязывается к эпохе**: он обязан пережить перезапуск браузера, иначе окно
фиксации внешнего эффекта останется незакрытым.

### Барьер инициализации

Обработчик запуска обязан сначала сменить эпоху и инвалидировать состояние прежней
и только затем допускать пульс и примирение:

```
загрузить сохранённое состояние
если это запуск браузера: сменить эпоху, инвалидировать состояние прежней
пометить управляющее состояние готовым

до готовности пульс, опрос и примирение не выполняются
```

Без барьера в коротком окне после запуска сохранённое соответствие успеет
представиться живым до смены эпохи.

### Частота

Минимум для повторяющихся сигналов — полминуты, поэтому выбранные 30 секунд лежат
на границе допустимого. Сигналы могут задерживаться, а сон устройства машину не
будит: после пробуждения пропущенный повтор срабатывает один раз и планируется
заново. Это согласуется с моделью аренды: 90 секунд — срок владения, а не гарантия
реального времени.

### Граница ответственности

**Примиритель управляет состоянием браузера, но не исполняет действий.** Он
открывает вкладки, берёт и снимает аренды, сообщает о endpoint и применяет план
управления. Отправка сообщений остаётся за конвейером действий и путём доставки.

Эта строка нужна не как новое решение, а как запрет: без неё часть исполнения
однажды незаметно переедет в `background.js`, и разделение, ради которого писался
9f, потеряется.

## 10h. Эпоха при переходе с 2.11.6

Расширение 2.11.6 эпохи не имело, поэтому правило «при обновлении не менять эпоху»
сохраняло бы несуществующее значение. Нужна операция обеспечения:

```
onStartup                       всегда новая эпоха,
                                состояние прежней инвалидируется

onInstalled (install | update)  эпоха есть  → сохранить
                                эпохи нет   → создать начальную,
                                              перезапуском браузера не объявлять

холодный старт worker           загрузить эпоху; если её нет из-за миграции
                                или первого запуска — создать до снятия барьера
```

Путь 2.11.6 → 4.5.0 проходит именно через вторую ветку.

## 10i. Контракт API

### Опрос: размеченное объединение, а не общий payload

```
pollKind = CONTROL_AGENT
  browserEpoch, extensionVersion
  → атомарно взять или продлить аренду владения
  → владелец: controlState = OWNER, план примирения
  → другая живая эпоха: CONTROL_AGENT_CONFLICT, ни плана, ни доставки

pollKind = ENDPOINT
  browserEpoch, endpointId, tabId, chatType,
  conversationId, projectId, url, title
  → проверить, что эпоха является текущим владельцем
  → наблюдение endpoint
  → и только затем разрешение доставки этому endpointId
```

Условно обязательных полей в общем теле не бывает: вид опроса задаётся явно, иначе
управляющий агент однажды получит обычную доставку.

### Время принадлежит серверу

```
controlHeartbeat.sentAt   только телеметрия и диагностика
lastSeenAt, leaseUntil    вычисляются сервером по времени приёма
```

Часы браузера отстают, убегают и меняются вручную. Если считать аренду по
клиентскому времени, агент продлевает владение собственными часами, и вся модель
перестаёт что-либо гарантировать. То же для пульса вкладки.

### Опрос вкладки без владения

Два разных случая, и лечатся они по-разному:

```
владельцем является другая эпоха   CONTROL_AGENT_CONFLICT
владельца нет либо аренда истекла  NOT_CONTROL_OWNER
```

Во втором случае конфликта нет: агент проспал и потерял аренду. Состояние
endpoint не меняется, доставка не выдаётся; service worker сначала восстанавливает
владение опросом вида `CONTROL_AGENT`, после чего опрос вкладки снова допустим.
Это отдельная строка приёмки для сценария со сном машины.

### Укорочение лога на сервере

```
<= 50 КиБ   полный текст
>  50 КиБ   первые 25 КиБ, отметка о числе пропущенных байт, последние 25 КиБ
            граница режется безопасно для UTF-8
```

Отрезать в разметке недостаточно: причина требования — медленный интерфейс, а он
останется, если браузер всё равно получит мегабайты. Полный лог доступен
отдельной выгрузкой.

Совпадение AUTO ERROR может оказаться в вырезанной середине. Поэтому API
возвращает выдержку вокруг совпадения и его позиции отдельно от укороченного
представления — иначе подсветка исчезнет именно на больших логах, где она нужнее
всего.

### Порядок проверок

Общего порядка после разметки нет: у двух видов опроса разные обязанности.

```
аутентификация запроса
→ проверка вида опроса и схемы
→ развилка
```

```
CONTROL_AGENT
  атомарный переход владения:
    владельца нет либо аренда истекла  → взять
    та же эпоха                        → продлить
    другая живая эпоха                 → CONTROL_AGENT_CONFLICT
  владельцу — план примирения
  доставки нет никогда

ENDPOINT
  требуется уже имеющееся владение:
    другая живая эпоха                 → CONTROL_AGENT_CONFLICT
    владельца нет либо аренда потеряна → NOT_CONTROL_OWNER
  и только затем наблюдение endpoint
  затем бизнес-авторизация доставки
  доставка только этому endpointId
```

Общий порядок «проверить владение, потом менять состояние» верен для `ENDPOINT` и
неверен для `CONTROL_AGENT`: этот запрос владение и получает. Требуй он владения
заранее, новая эпоха не стала бы владельцем никогда.

Для `ENDPOINT` порядок остаётся жёстким: поздний запрос прежней эпохи не должен
успеть обновить время наблюдения, закрыть endpoint или забрать доставку прежде,
чем сервер обнаружит, что она больше не владелец.

### Закрытие вкладки

```
эпоха является владельцем        CLOSED, привязанность освобождается
эпоха владельцем не является     состояние браузера не меняется
endpoint уже CLOSED или EXPIRED  идемпотентно, ничего не делать
```

Так правило «состояние браузера меняет только текущий владелец» получает
проверяемую форму.

### Четыре семейства маршрутов

| Семейство | Что обслуживает |
|---|---|
| управление | активация, состояние сессий, `restartGeneration`, план примирения |
| браузер | пульс агента, пульс вкладки, закрытие вкладки, явный выбор endpoint для чата сессии |
| исполнение | действия, разрешение `OUTCOME_UNKNOWN` оператором, неизменяемые манифесты доставки |
| артефакты | список и фильтры файлов, загрузка и выбор для `FILE_NEEDS_ATTENTION`, скачивание файла и группы, выгрузка отправленных вложений |

### Выбор endpoint — не переименование закрепления

`api_endpoint_pin:808` переименовать нельзя. Прежнее закрепление — глобальное
свойство endpoint из 4.4.0, новая операция — отношение чата сессии к endpoint:

```
selectEndpoint(sessionId, bindingId, endpointId)
```

с повторной живой проверкой идентичности и авторизации. Записывать
`approvedEndpointId` обратно в endpoint она не должна: это поле удалено вместе с
механизмом устаревания.

### Граница шлюзов

**Аутентификация запроса не является авторизацией действия.** Запрос от законного
владеющего агента не даёт права отправить что-либо, если это запрещают
включённость профиля, привязка или правило 5.3. Это отправная точка раздела про
шлюзы.

## 10j. Интерфейс

Строится от состояний, требующих решения оператора, а не от страниц.

| Состояние или функция | Представление |
|---|---|
| активация профиля | «Автоматически», «Запущено», «Остановлено»; действующее намерение и фактическое состояние сессии |
| расхождение редакций | запущенная и текущая редакции, кнопка перезапуска |
| `CONTROL_AGENT_CONFLICT` | заметное глобальное предупреждение о втором управляющем браузере |
| `ENDPOINT_AMBIGUOUS` | кандидаты и явный выбор для пары сессии и привязки |
| `OUTCOME_UNKNOWN` | «Считать отправленным» и «Отправить заново» |
| `FILE_NEEDS_ATTENTION` | загрузить файл либо выбрать артефакт |
| подменённый файл | видимое указание фактического артефакта и причины подмены |
| вкладки | фильтр «скрыть офлайн» |
| Runs | фильтр по профилю, отметка о повторе, укороченный лог |
| доставка | выгрузка вложений строго по неизменяемому манифесту |
| файлы | фильтры по профилю и имени, сортировка, групповая выгрузка |
| команды | карточки вместо сырого JSON директив |

**«Скрыть офлайн» — только фильтр отображения.** Он не скрывает
`CHAT_UNRESPONSIVE`, `REVOKED`, `CONFIG_CHANGED`, неоднозначность и прочие
состояния, требующие внимания, и не меняет состояние реестра. Иначе полезная
функция станет способом спрятать неисправность.

## 10k. Шлюзы

Не один общий шлюз, а три независимых уровня:

```
1  аутентификация запроса     кто вообще обратился по HTTP
2  владение браузером         вправе ли эта эпоха менять состояние браузера
3  бизнес-авторизация         разрешено ли именно это исполнение или отправка:
                              включённость профиля, существование и включённость
                              привязки, идентичность, зафиксированный состав
                              сессии, жизненный цикл действия, правило 5.3,
                              действующая включённость вкладки
```

Разделение важно с обеих сторон. Примиритель проходит первые два уровня и **не
получает через это никаких бизнес-прав**.

Обратное тоже верно, но точнее, чем кажется. Владение не входит в бизнес-шлюз:
`authorize_delivery` его не проверяет, иначе временная потеря аренды превратила бы
ожидающую доставку в ошибку прав. Уровень 2 запрещает не отправку как таковую, а
получение и исполнение браузерной доставки чужой или устаревшей эпохой.

`selectEndpoint` состояние браузера не меняет — она меняет серверное отношение
чата сессии к вкладке, и консоль оператора управляющей эпохой не является. Шлюз
владения к ней не применяется. Проверяется сам объект выбора: вкладка не в
`CLOSED` или `EXPIRED`, соответствует идентичности и конфигурации и остаётся
допустимым кандидатом.

Уровень 2 у двух видов опроса разный, и одинаковым шлюзом его называть нельзя:

```
CONTROL_AGENT          арбитраж и переход владения
ENDPOINT, закрытие     требование уже имеющегося владения
изменения примирителя  выполняются только по плану, выданному владельцу
```

Привязка к существующему коду:

| Уровень | Точка |
|---|---|
| 3, вход | `run_profile_context.authorize_execution:87` |
| 3, выход | `run_profile_context.authorize_delivery:199` |
| 2 | новый шлюз в `api_delivery_poll:628`, **до** `endpoint_registry.observe:98` |
| 1, затем 3 | `selectEndpoint`: аутентификация оператора и живая бизнес-проверка |

Порядок в опросе принципиален: шлюз владения стоит до наблюдения, иначе запрос
прежней эпохи изменит состояние раньше, чем будет отвергнут.

## 10l. Факты, установленные чтением кода

Четыре класса, не три. Четвёртый обнаружился при проверке и исправляет ошибку
инвентаризации.

### Приём Run находится не там, где было указано

`scan_fingerprint:191` только хэширует уже готовый список для вебсокета. Run
создаёт **receiver**: `server.py::_result` формирует идентификатор безусловно и
создаёт каталог с `exist_ok=False`. Дедупликации там нет.

Следовательно в receiver переезжают обе вещи:

```
срез 1   отпечаток входящего разбора, поиск дубля в окне,
         счётчик повторов, явный повтор, создание Run только при отсутствии дубля
срез 5   закрытый приём: новый каталог Run не создаётся
```

Без правки receiver правило «закрыть приём новых Run» невыполнимо.

### Тишина начинается с захвата, а не со статуса задания

Мост сначала захватывает задание, и только затем работает с DOM; на сервере
захват хранится через токен лизы, владельца и срок. Поэтому предикат тишины
двухфазный:

```
1  приём новых Run закрыт
2  выдача новых заданий закрыта
3  уже захваченным заданиям разрешено закончить: их события ещё принимаются
4  локальная тишина: нет исполняющегося шага и живого подпроцесса
5  браузерная тишина: нет заданий с активным захватом
                      и нет вложений в состояниях передачи
6  и только затем полный барьер и переключение
```

**Истечение лизы тишины не доказывает.** Сервер очищает просроченный захват, но
приостановленная браузером задача теоретически может продолжиться, а отдельной
серверной проверки лизы непосредственно перед нажатием нет. Захват, истёкший во
время слива, не засчитывается: выкат останавливается и требует сброса
соответствующего браузерного контекста.

Отсюда барьер имеет два режима, а не один:

```
СЛИВ      новые задания не выдаются, события захваченных принимаются
БАРЬЕР    после доказанной тишины, изменения состояния браузера
          старым протоколом не принимаются вовсе
```

Полный барьер сразу лишил бы уже выданные задания возможности честно сообщить об
отправке, и мы сами создали бы неопределённость.

### Защиты от несогласованных версий сейчас нет

`api_delivery_poll:628` не знает ни версии расширения, ни вида опроса и вызывает
наблюдение сразу. Существующая проверка совместимости в расширении относится к
receiver и на консоль не распространяется: мост передаёт только токен.

Значит это **новая обязанность**, а не перестановка существующей проверки:

```
несовместимый или отгороженный протокол
→ отказ до арбитража владения
→ отказ до наблюдения
→ ни плана, ни доставки, ни изменения состояния браузера
```

### Миграция конфигурации

Валидатор профиля пересобирает документ из известных полей, поэтому неизвестные
поля при сохранении исчезают. Фактическое имя параметра в основании —
`endpointWaitTimeoutSec`, дизайн использует `endpointWaitTimeoutSeconds`. Каталог
`config/` при ломающем выкате сохраняется, значит это настоящая миграция:

```
нового имени нет, старое есть   перенести значение
есть оба и различаются          миграцию остановить, не угадывать
```

`files.attentionTimeoutSeconds` обязан быть принят валидатором, иначе интерфейс
покажет параметр, а следующее сохранение его выбросит.

### Основание расширяется до восемнадцати файлов

К тринадцати добавляются:

```
server.py                     приём Run, дедупликация, закрытие приёма
execution_error_detector.py   хранит id, описание и выдержку; нужны позиции
profile_store.py              пересборка документа, имя параметра доставки
chat_bindings.py              нормализует endpointPolicy и approvedEndpointId
profile_resolver.py           содержит ветку approved_endpoint
```

Последние два меняются обязательно: механизм закрепления и одобрения в 4.5.0
удаляется, оставить их прежними нельзя.

Receiver входит в основание наравне с r7:

```
receiver 2.10.0, снимок платформы pro2
server.py
sha256 = 0f3d79249e98928391a1b009c1b414e0f758cda9cc29c3037547fc0990408a21
```

Хэш `30f1b11c…` относится к прежнему дереву pro1 до перебрендирования и
основанием не является; смешивать их нельзя.

### Требования к конечному комплекту

Два места конечного комплекта не должны сокращаться до уже названных случаев.

**Таблица миграции параметра доставки закрывает все пять состояний**, а не два:

```
старое есть, нового нет                перенести
оба есть, значения совпадают           оставить новое, старое удалить
оба есть, значения различаются         остановить миграцию, не угадывать
старого нет, новое есть                оставить новое
ни одного нет                          взять из фактического умолчания новой схемы
```

Последняя строка выводится из валидатора при составлении точки врезки, а не
назначается в документе.

**Предикат тишины называет конкретные поля основания** и разделяет три вопроса:

```
можно ли продолжать слив
можно ли объявить браузерную доставку тихой
можно ли включать полный барьер
```

Случай «захват истёк во время слива» — отдельный **отрицательный** случай приёмки:
тишина не доказана.

Идентификаторы случаев приёмки назначаются при написании точек врезки, а не после:
тогда строка `api_delivery_poll` сразу получает проверки отказа по версии до
наблюдения, `NOT_CONTROL_OWNER`, `CONTROL_AGENT_CONFLICT`, слива, барьера и позднего
запроса прежней эпохи, и матрица приёмки не сможет разойтись с картой изменений.

## 11. Явные не-цели

Не делаем в 4.5.0: постоянный идентификатор браузера или машины; автоматический
подхват незнакомой переписки; горячую перезагрузку конфигурации в запущенную
сессию; закрытие вкладок при остановке; хранение значений секретов где-либо,
кроме `config/secrets/`.

## 12. Остальные разделы

Осталось четыре, все прикладные:

```
Точки врезки в r7 и 2.11.6 с полными хэшами основания
Миграция с 4.4.0 r7 и 2.11.6
Матрица приёмки по срезам
Откат каждого среза
```

### Форма строки точки врезки

```
срез
релиз-основание
файл
полный sha256 основания
символ
точный диапазон строк

текущая обязанность
обязанность в 4.5
изменение: добавление | замена | удаление

ссылки на контракты
что менять нельзя
последствие для миграции
идентификаторы случаев приёмки
последствие для отката
```

Ссылки на контракты отличают «меняем обязанность» от «файл просто участвует».
Например строка `api_delivery_poll:628` ссылается на 9a, 9c, 10i и 10k и тем самым
объясняет, почему проверка владения обязана стоять до наблюдения.

### Однонаправленные преобразования миграции

Каждое получает зеркальную строку приёмки:

```
прежнее закрепление и approvedEndpointId не переносятся как привязанность
у 2.11.6 нет эпохи, работает ensureEpoch
снимки и хранилище файлов создаются только тем сущностям,
  которым они нужны по правилам своего среза
```

**Включённые вкладки 2.11.6.** Сессий там нет, поэтому `enabledTabs[tabId] = true`
это старое операторское включение. Но поведение `chrome.storage.session` при
обновлении расширения мы намеренно оставили неустановленным, поэтому перенос
условный:

```
старое значение доступно, true, вкладка существует сейчас
  → ручная причина новой миграционной эпохи

старое значение недоступно
  → ручную причину не угадывать: ни по номеру вкладки,
    ни по статусам, ни по факту открытой вкладки

false или отсутствует
  → причины нет
```

В худшем случае теряется ручное включение; ложного разрешения на исполнение не
появляется никогда. Если сохранять ручные включения через обновление обязательно,
нужен предварительный экспорт из 2.11.6 — это отдельная работа, а не следствие.

### Старые Run

Совместимости со старыми Run нет и не проектируется. Это решение принято в самом
начале работы над pro2 и действует без изменений: сохранённые Run одноразовы.

```
каталоги Run прежних схем не читаются, не мигрируются и не исполняются
при выкате ломающего среза data/ очищается целиком
config/, secrets/, runtime/token.txt и logs/ не трогаются
```

### Срез 5 — вторая атомарная граница

Как и срез 2, срез 5 устанавливается сервером и расширением **вместе**. Сервер в
нём начинает жить с идентичностью действия и доставки, новыми схемами и
`OUTCOME_UNKNOWN`, а расширение получает долговечный журнал доставки. Включение
одной половины раньше другой лишает `OUTCOME_UNKNOWN` его единственной гарантии.

```
срез 2  реестр по endpointId, владение, привязанность
        endpointId, эпоха, закрытие вкладки, аренды
срез 5  идентичность действия и доставки, новые схемы, OUTCOME_UNKNOWN
        журнал доставки, разрешение файлов среза 3b
```

### Атомарность ломающего выката

Проверка и очистка — не две раздельные операции: между ними придёт новый Run, и
миграция сотрёт его сама.

```
закрыть приём новых Run
→ дождаться тишины
→ повторно убедиться, что приём закрыт и новых Run не появилось
→ очистить data/
→ установить одной границей: консоль, разрешение файлов, расширение
→ подтвердить совместимость сервера и расширения до первой новой доставки
→ открыть приём
```

Тишина имеет **два** условия, а не одно:

```
нет исполняющегося локального шага
нет браузерной доставки, уже выданной расширению и незавершённой
```

Второе существенно: `delivery_manager` отделяет задание доставки от локального
исполнения, поэтому задание, уже забранное вкладкой, очисткой каталога не
отзывается — сообщение всё равно уйдёт. Точный предикат выводится из фактических
состояний заданий при написании точек врезки, а не угадывается заранее.

### Несогласованные версии во время замены

Закрытие приёма защищает `data/`, но не состояние браузера. Точка врезки
`api_delivery_poll:628` обязана доказать одно из двух: либо несовместимая версия
расширения отвергается **до** арбитража владения и до наблюдения, либо на время
замены половин существует отдельный барьер браузерной плоскости. Одного «не
выдавать новую доставку» мало: старое расширение не должно успеть обновить
endpoint или получить план примирения от новой половины.

### Откат ломающего среза

Откат тоже разрушителен. После того как новая версия приняла хотя бы один Run, в
`data/` лежат данные новой схемы, понимать которые прежний код не обязан.

```
закрыть приём
→ дождаться тишины по обоим условиям
→ очистить data/ новой схемы
→ очистить журнал доставки
→ инвалидировать всё пространство состояния вкладок 4.5:
     эпоха, соответствия tabId → endpointId,
     ручные причины, кэш сессионных аренд
→ привести enabledTabs к явно выключенному состоянию
→ переключить маркер консоли на предыдущий
→ откатить расширение до согласованной версии
→ открыть приём
```

Чистить только журнал недостаточно. Пока работает 2.11.6, она эти ключи не
обслуживает: вкладки закрываются и открываются, номера переиспользуются. При
повторном переходе на 4.5 `ensureEpoch` увидит сохранённую эпоху и примет
протухшее соответствие за состояние той же браузерной сессии. После инвалидации он
честно пойдёт по ветке «эпохи нет — создать начальную».

`enabledTabs` приводится к выключенному состоянию по той же причине, по которой
перенос вперёд условный: сохранение `storage.session` не установлено, и оставленное
содержимое может вернуть разрешение, существовавшее до 4.5. Обратный перенос
ручных включений, если он понадобится, задаётся отдельным явным преобразованием
только для существующих вкладок.

Журнал доставки живёт вне `data/` и переживает перезапуск браузера, поэтому его
судьбу откат обязан определить: серверных доставок, которым соответствуют его
записи, после отката не существует. Очищать его **до** тишины нельзя — так
уничтожается единственное свидетельство состояния `DISPATCHING` ровно в том окне,
ради которого вводился `OUTCOME_UNKNOWN`.

Общее правило:

```
разрушать состояние допустимо только после закрытия приёма
и завершения всех внешних эффектов текущего поколения
```

Потеря данных при откате — не только удалённое прежнее содержимое `data/`, но и
Run, созданные уже после перехода. Это согласуется с одноразовостью Run, но в
матрице отката должно быть написано прямо.

Поэтому в 4.5.0 нет ни читающей, ни исполнительной совместимости, нет правил для
Run без снимка и нет условий входа в срез 7 по остаткам старых Run. Каждый Run,
существующий после выката, создан уже новой схемой.
